# REV-04 — Phase 04 Authentication and permissions (Opus review)

Date: 2026-11-12. Scope: per `REV-04-PACKET.md` (commits 3761dbf..HEAD plus uncommitted WP-04.6 tests). Method: code and test reading only; no suites executed by the reviewer.
Against: ADR-050..052, INTERFACES §2-3, SECURITY §2-3, TS-S01/S02/S04.

## Findings

1. apps/api/src/modules/identity/adminUsers.ts:264-309, roles.ts:79-95, adminUsers.ts:226 — HIGH — privilege escalation by any `users.manage`/`roles.manage` holder (ADMIN): it can compose a custom role with any permission (`tally.posting.manage`, `report.financial.view`, `*.approve`), assign it to a new user whose temporary password it chose, or issue a reset code to an ACCOUNTANT and complete it itself, so it gets every non-OWNER power. That contradicts INTERFACES §3 "ADMIN: no financial approvals" and defeats the no-self-approval split. — Fix (unless the owner records acceptance in STATUS before the gate): add `ELEVATED_PERMISSIONS` in catalogue.ts = users.manage, roles.manage, settings.manage, audit.view, tally.connector.manage, tally.mapping.approve, tally.posting.manage, finance.edit, report.financial.view and every `*.approve`. A non-OWNER caller may not (a) create or update a custom role that holds one, (b) assign a role that holds one, or (c) edit, disable, unlock, reset, force-logout or revoke the device of a user who holds one. Answer 403 `FORBIDDEN`, reason `ELEVATED_ONLY`, using the same checks as `assertManageable`. Add tests for (a), (b), (c) and an ADMIN-on-ADMIN case. Replace the "Open for review" sentence in INTERFACES §2 (identity guards). Effect with the default matrix: ADMIN manages DRIVER and SUPERVISOR accounts; OWNER manages ACCOUNTANT, FACTORY_MANAGER, ADMIN and OWNER accounts.
2. apps/api/src/modules/identity/security.integration.test.ts:235-236 — MEDIUM — vacuous assertion: `me.permissions` is an array of grant objects, so `not.toContain('report.financial.view')` can never fail. TS-S01 is not actually proven at the API boundary. — Fix: assert on `me.permissions.map((g) => g.permission)`. Also check that it holds only OWN scope.
3. apps/web/src/app/App.tsx:29-32 + apps/web/src/offline/syncEngine.ts:213-236 — MEDIUM — after an offline start the runtime runs while `verified=false` with no CSRF token. A push raced by the `online` event gets 403 CSRF, which counts as an attempt and records PUSH_FAILED. This is also the only thing that stops a tampered `tradex.identity` (user.id edited) from pushing another local user's outbox with the current cookie. — Fix: the engine must not push or pull while `sessionStore.csrfToken` is undefined; treat that like the 401 pause and resume on verify. Add a unit test for it.
4. apps/api/src/modules/identity/routes.ts:38, adminRoutes.ts:79, auth.ts:112-120 — MEDIUM (deferred to Phase 14, gate item there) — behind a proxy without `trustProxy`, every client has the proxy IP. Then 20 failed logins from anyone lock out all users for 15 minutes, and the 30/min login cap and 20/15 min reset cap become global. — Fix: in the Phase 14 WP that introduces Caddy, set `trustProxy` to the exact proxy address or hop count (never `true`) and add a test that a forged `X-Forwarded-For` from a non-proxy source is ignored. Never deploy behind a proxy before then.
5. apps/api/src/modules/identity/auditView.ts:10-57 — MEDIUM (deferred to Phase 10) — `GET /audit` returns `before`/`after` of every entity to every `audit.view` holder (ADMIN). Once expense, advance and finance rows are audited, ADMIN sees amounts it has no right to view. — Fix before the first financial module writes audit rows: filter or redact rows by an entity-type → view-permission map (no rows for an unmapped type without OWNER). Record it in PHASE-10 context.
6. apps/api/src/modules/identity/catalogue.ts:115,126 — LOW — the literal patterns `tally.*` and `*.view` give ACCOUNTANT `tally.connector.manage` (register or revoke the Tally agent) and `audit.view`. The snapshot now pins this. — Fix: owner confirms; then list both explicitly in INTERFACES §3 so the matrix does not depend on a wildcard.
7. apps/api/src/modules/identity/adminUsers.ts:672-688 (also auth.ts:229-247) — LOW — a known username triggers an extra query plus an audit-row transaction that an unknown username does not, so the public reset and login endpoints leak whether a username exists through timing. — Fix: accept it (usernames are low secrecy) and note it in SECURITY §2, or do equal work on both paths.
8. apps/api/src/modules/identity/routes.ts:49 — LOW — the old session is retired only when the cookie resolved to a ctx. A cookie bound to another device (X-Device-Id mismatch) survives the new login. — Fix: revoke by `hashToken(requestSessionToken(...))` whenever a well-formed cookie is presented.
9. apps/api/migrations/0004_identity.sql:19-21 — LOW — status `LOCKED` and `locked_until` are never set: lockout is derived from `login_attempt`. — Fix: document them as unused in DATA_MODEL §2, or drop them in a later migration. No behaviour change now.
10. apps/api/src/plugins/rateLimit.ts:39-40 — LOW — the doc comment for `consume` sits above `refund`. `refund` pops the newest hit, not the caller's own; under concurrency this is harmless. — Fix: move the comment.

Verified as correct: 256-bit tokens with only the SHA-256 stored; a new token on every login, with the carried session revoked; HttpOnly, SameSite=Lax, and Secure plus `__Host-` in production; HMAC double-submit CSRF bound to the session and judged by the matched route; lockout serialised with advisory locks; dummy Argon2 hash for unknown users; reset code hashed per user, single use via a conditional update, 30 minutes, every session revoked; LAST_OWNER serialised; `onRoute` refuses any route without a declaration, with the inventory pinned by a test; out-of-scope answers 404 with the same body as a missing record (TS-S02); expired, revoked, logged-out, force-logged-out and device-revoked sessions answer 401 on every route kind (TS-S04).

## Open questions — recommendations

1. Device ownership: accept shared devices (factory tablets) and do not refuse or re-bind. Add `shared_device: true` to the `auth.login` audit when `device.user_id` differs. In Phase 12, verify that idempotency, conflicts and pull cursors key on `ctx.userId` plus device, never on the device owner alone.
2. ADMIN escalation: not acceptable as built. Implement finding 1 (the ELEVATED rule; OWNER stays unrestricted), or the owner records explicit risk acceptance in STATUS.
3. Local identity copy: UI only. It holds no token, the cookie is httpOnly, and the server re-authorizes every request, so tampering grants no server authority. The real exposure on a shared device is a phone that was never signed out (14-day idle session), and unencrypted IndexedDB records readable by whoever holds the phone (accepted). Close the push race with finding 3.
4. `request.ip` behind a proxy: the limits and IP lockout become global and can be used for DoS. Keep the current behaviour for loopback/dev only and make `trustProxy` a Phase 14 gate item (finding 4).
5. Session and reset hygiene: pass. Only LOW items 7 and 8 remain.
6. Route declarations and 403 vs 404: pass. Permission 403s happen before any lookup. OWNER_ONLY/ELEVATED_ONLY 403s after a lookup reveal existence only to `users.manage` holders, who can list users anyway.

## Verdict

APPROVED_WITH_FIXES. Before the Phase 04 gate, Sonnet fixes finding 1 (or obtains recorded owner acceptance), finding 2 and finding 3. Findings 4 and 5 are recorded as gate items for Phase 14 and Phase 10. LOW items are optional.

## Resolution (Sonnet, 2026-11-12)

- Finding 1 (HIGH): FIXED as recommended. `ELEVATED_PERMISSIONS` in `identity/catalogue.ts`; `assertManageable` is now async and covers elevated holders; `assertGrantablePermissions` guards role create and update; `resolveAssignments` refuses elevated roles; own record exempt. Tests: `admin.integration.test.ts` "elevated permissions are owner-only" (6 tests). INTERFACES §2 guard text replaced. Consequence the owner should know: an ADMIN no longer manages ACCOUNTANT, FACTORY_MANAGER or other ADMIN accounts (OWNER does). Owner may still relax this by editing `ELEVATED_NAMED`; it is a code constant, not data.
- Finding 2 (MEDIUM): FIXED. `security.integration.test.ts` now asserts on grant codes and scopes.
- Finding 3 (MEDIUM): FIXED. `createSyncEngine` takes `hasCredentials`; the app runtime passes "CSRF token present". Without it a run is skipped (`no-session`), no attempt is counted, and `SessionEffects` triggers a run after `/auth/me` verifies. Unit test added in `syncEngine.test.ts`.
- Finding 4 (MEDIUM): recorded as a Phase 14 gate item (PHASE-14 section C/D).
- Finding 5 (MEDIUM): recorded as a Phase 10 carry-over (PHASE-10 section B).
- Findings 6-10 (LOW): not changed. 6 needs an owner confirmation of the ACCOUNTANT matrix (wildcards `tally.*`, `*.view`); 7, 9, 10 are documentation or comment items; 8 (retire a cookie bound to another device on login) is cheap and can ride along with the next identity change.
- Open question 1 (shared devices): accepted as the reviewer recommends; the `shared_device` audit flag and the Phase 12 keying check are not yet done and are carried to WP-12.
