# Security Architecture (v1.0)

## 1. Trust boundaries

| Boundary | Threats | Controls |
|---|---|---|
| Internet ↔ Caddy | MITM, scanning, DoS | TLS 1.2+ (auto certs), HSTS, only 80/443 open, security headers, request size limits |
| Browser ↔ API | session theft, CSRF, XSS, IDOR | httpOnly Secure SameSite=Lax cookie, CSRF header, CSP, server-side authz + row scope, NOT_FOUND for out-of-scope |
| Agent ↔ API | impersonation, replay, rogue second agent | registration code (one-time, 15 min, hashed), ECDSA P-256 signed requests, timestamp ±300 s, nonce table, lease epoch, revoke |
| Agent ↔ Tally | remote access to Tally | loopback only, firewall inbound block, agent refuses non-loopback host |
| API ↔ Postgres | SQL injection, privilege abuse | Kysely parameterised queries only (raw `sql` tagged templates only, never string concat), separate migration role and app role, audit_log INSERT-only |
| VPS host | compromise, data loss | SSH keys only, no root login, ufw, unattended security upgrades, Docker non-root containers, encrypted off-site backups |

## 2. Authentication

- Argon2id (`@node-rs/argon2`, memoryCost ≥ 19456 KiB, timeCost ≥ 2, parallelism 1). Rehash on login if params change.
- Password policy: ≥ 10 chars, reject top-10k common passwords list (bundled file), no composition rules.
- Login rate limit: 5 failures / 15 min per username → lock 15 min; 20 / 15 min per IP. Generic error message.
- Sessions: 256-bit random token; DB stores SHA-256 only; idle expiry 14 days sliding (drivers in the field
  are offline for long), absolute 30 days; revoke on password change, user disable, admin force-logout.
- Password reset: admin issues one-time 8-char code (hashed, 30 min, single use) — OD-032 may add a channel.
- `must_change_password` on first login (administrator-set temporary password). A reset completes with a password the user chooses, so it clears the flag; completing a reset also revokes every session and clears the lockout.
- Offline: the PWA never stores the password. Offline use relies on the existing cookie; if the session
  expired while offline, local capture continues but sync waits for re-login **by the same user**
  (outbox entries are tagged with user_id; a different user cannot push them).
- Web client (WP-04.5): the CSRF token lives in memory only and is re-read from `GET /auth/me` on every page load.
  For an offline start the app keeps a local copy of who is signed in (`tradex.identity` in localStorage: user,
  role names, permission grants; no password, no session token, no CSRF token) so local capture works; it is
  UI-only (the API authorizes everything), is removed on logout, on a 401 and when `/auth/me` answers 401, and the
  app re-checks it against the server every 30 s and on `online`. Logout needs the server (a logout that only
  cleared the phone would leave a live session): offline, the user stays signed in and is told why. A 401 on any
  request ends the UI session, clears the query cache and shows the login page.

## 3. Authorization

Permission + scope check in every route via `authorize(permission, scopeResolver)` (INTERFACES §3).
Services re-check state-machine rights (e.g., no self-approval). List queries always include scope
predicates generated by one shared helper — never ad-hoc. Driver role sees no `report.financial.*`, no other
drivers' records, no Tally balances. Authorization tests are mandatory per endpoint (QUALITY_GATES).

## 4. Web protections

- CSP: `default-src 'self'; img-src 'self' blob: data:; connect-src 'self'; frame-ancestors 'none';
  object-src 'none'; base-uri 'self'` (no inline scripts; Vite build compatible).
- Headers: HSTS, X-Content-Type-Options nosniff, Referrer-Policy same-origin, Permissions-Policy (camera self only).
- React escaping; no `dangerouslySetInnerHTML`. Excel export: prefix cells starting with `= + - @` with `'`
  (formula injection).
- CSRF: double-submit token returned by `/auth/me` and sent as `X-CSRF-Token`; checked on all non-GET.
- Rate limits (in-memory per process, acceptable for single instance): login, reset, register, upload (30/min/user).

## 5. Files

Allowed: JPEG, PNG, WebP, PDF (magic-byte check, not extension), ≤ 10 MB (client compresses photos to
≤ 1600 px / ~300 KB). Stored outside web root by sha256 key; served via API with auth and
`Content-Disposition`; images re-encoded server-side (strips EXIF GPS) — keep original only if owner opts
in. Filenames never used as paths. Bank statements (CSV/XLSX) parsed in a size/row-limited parser.

## 6. Secrets

- Server: `.env` files on VPS only (`chmod 600`), never in git; `deploy/env.example` documents keys.
  Required: `DATABASE_URL`, `SESSION_SECRET` (cookie signing), `BACKUP_REPO_PASSWORD`, object storage keys.
- Agent: only its private key (DPAPI LocalMachine, ACL). No Tally password stored (Tally HTTP needs none
  on loopback; if the company has a Tally password configured, agent does not bypass it — OD-007).
- CI: GitHub Actions secrets only for deploy (Phase 14). Secret scanning: `gitleaks` in CI and pre-commit.

## 7. Audit and privacy

- Every mutation writes `audit_log` in the same transaction (actor, before/after diff, device, request id).
- Personal data minimised: worker/driver phone, licence no.; no Aadhaar/bank account numbers stored in v1
  unless owner decides (then encrypted column with pgcrypto + app key).
- Retention: OD-033. Logs 30 days on VPS.

## 8. Dependencies and supply chain

`pnpm audit --prod` and `dotnet list package --vulnerable` in CI (fail on high/critical with documented
exceptions), lockfiles committed, Renovate/Dependabot optional, Docker base images pinned by digest,
agent binaries signed or at least SHA-256 published with each release.

TS-S01..TS-S07 in QUALITY_GATES §4. Phase 14 adds an OWASP ASVS L1-oriented checklist review (Opus).
